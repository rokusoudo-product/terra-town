# terra-town — 名所・固有オブジェクト（大量配置POI）システムの定義

> 本書は [Issue #6](https://github.com/rokusoudo-product/terra-town/issues/6)「名所・固有オブジェクトシステム」の受け入れ基準を満たすための設計ドキュメント。
> `specs/001-mvp/spec.md` FR-3・§3.1（価値提案 V-B: 土地の固有性）・§5（マップ設計方針の「特殊マス/名所」）を具体化する。
> [Issue #4](https://github.com/rokusoudo-product/terra-town/issues/4)（`docs/opening_points.md` §7）で「固有名所の現地限定は不採用、興味を引くオブジェクトを大量配置してV-Bを実現する」と方針転換された内容の実装本体にあたり、`specs/001-mvp/spec.md` 本文の該当箇所も本書とあわせて改訂する。
> データモデルは `specs/001-mvp/plan.md` §3.2（地域パック内の `poi` テーブル）・§6（`collection` エンティティ・名所図鑑 #6/#12統合）で先行して枠組みが定義済みであり、本書はその仕様上の正とする。
> 実装言語・ゲームエンジン・地図SDKは `specs/001-mvp/plan.md`（ゲート②承認済み・Flutter＋MapLibre）に従う。
> 実装フェーズでは `C:\Users\moets\.claude\GPS_ARCHITECTURE.md`（`core/` は `location/` を import しない一方向依存）に従うこと。オブジェクトの種別判定・収集判定・産出/ポイントボーナス計算・図鑑記録は `core/` 相当の純粋ロジックとして実装し、地域パック（POIテーブル）の読み込みや地図描画は `location/` 相当のモジュール／表示レイヤーに置く。`core/` へは事前に判定済みの POI レコード（種別・座標由来の `HexId`・ボーナス有無フラグ）のみを渡す。

## 1. 背景

- `specs/001-mvp/spec.md` FR-3「実在の名所/土地利用と連動した固有オブジェクトを現地開示時に出現させる」は要件のみで詳細未定義だった。
- [Issue #4](https://github.com/rokusoudo-product/terra-town/issues/4) の代表回答（2026-07-22）により、当初 spec.md §3.1 が前提としていた「固有名所は現地限定（行かないと手に入らない）」という制約は**不採用**となった。理由: 現地限定にすると立入禁止・遠隔地等、行けない場所の方が多く離脱要因になるため。
- 代わりに、「行ってみたい」「ここにはこんなものがある」と興味を引くオブジェクトを地図上に**大量配置**する方向で V-B（土地の固有性）を実現する方針に転換された（希少な現地限定コレクションではなく、豊富な発見コンテンツで動機づけ）。
- 本書はこの方針転換を受けて、オブジェクトのデータソース・種別・配置密度・出現条件・コレクション連携を確定する。

## 2. データソースと種別（一般オブジェクト / ボーナスオブジェクト）

オブジェクトは**一般オブジェクト**と**ボーナスオブジェクト**の2種別に分類する。いずれも `specs/001-mvp/plan.md` §3.2 の地域パック内 `poi(id, lat, lon, kind, name)` テーブルに集約し、実行時ではなく **CI（パック生成時）に事前計算**する（`docs/terrain.md` §5 の地形判定と同じ「決定論的な事前計算」思想に揃える。plan.md §4 参照）。

### 2.1 一般オブジェクト（MVPの主力・大量配置の担い手）

- **データソース: OSM（tourism=* 等の観光POIタグを主体）**。plan.md §3.2 の「名所 POI（OSM 観光POI 抽出）」を具体化する。
- 2層のタグ優先度で抽出する（`docs/terrain.md` §5 の優先順位表と同じ考え方）。

| 層 | 役割 | 判定タグ例（OSM） |
|----|------|-------------------|
| 主要層（Tier 1） | 「名所らしさ」が明確な地物。全エリアで無条件に採用 | `tourism=attraction`／`viewpoint`／`artwork`／`museum`／`gallery`／`zoo`／`theme_park`、`historic=monument`／`memorial`／`castle`／`ruins`／`archaeological_site`、`leisure=park`（一定面積以上） |
| 補完層（Tier 2） | 主要層だけでは密度が不足する地域（郊外・山間部等）を補うための広めのタグ。地域内の主要層密度が §3 の目標密度を下回る場合のみ採用 | `amenity=place_of_worship`（神社・寺・教会）、`historic=wayside_cross`／`milestone`、`man_made=tower`／`lighthouse`、`natural=tree`（`denotation=natural_monument` 等の名木指定のみ）、`tourism=picnic_site`／`information` |

- Tier 2 はあくまで**実在の地物**に限定し、完全な架空オブジェクト生成は行わない（V-A「実地図連動＝現実の再発見」との整合を保つため）。
- 抽出ルールは初期版であり、実データ検証（過剰抽出・地域偏在）を経て plan/tasks 工程で精緻化する（`docs/terrain.md` §5 と同様の扱い）。

### 2.2 ボーナスオブジェクト（少量の独自キュレーション）

- **データソース: OSM 抽出結果 ＋ 少量の独自キュレーションリストの併用**（Issue #6 決定事項に準拠）。
- 判定条件（AND）:
  1. OSM 上で `tourism=attraction` 等の一般オブジェクト抽出条件を満たし、かつ `wikidata=*` タグを持つ（＝Wikidata上に独立記事があるレベルの著名性の一次シグナル）。
  2. **かつ**、開発者が管理する少量の独自キュレーションリスト（例: 東京タワー・皇居・富士山・著名な城郭・国宝級文化財等、全国的な知名度を持つ地物を数十〜百件規模で列挙した allowlist。`wikidata` ID または名称で照合）に含まれる。
- 自動判定のみに頼らず allowlist を必須とする理由: `wikidata` の有無だけでは知名度のばらつきが大きく（地方の小規模施設にも付与されている場合がある）、「有名観光地はボーナス」という受け入れ基準の意図（特別感の担保）を自動抽出だけでは満たせないため。
- allowlist は plan/tasks 工程でデータファイル（例: `bonus_landmarks.csv`：`wikidata_id, name, kind`）として管理し、パック生成CIで OSM 抽出結果と突き合わせる。
- 一般オブジェクトとの主な違いは §4（コレクション連携）の報酬倍率のみとし、出現条件（§3）は一般オブジェクトと同じ枠組みに従う。

### 2.3 ライセンス

- OSM 由来データは ODbL に従う（`specs/001-mvp/plan.md` §9 に既出「名所 POI（#6）: OSM 由来のため ODbL」）。派生データ・キャッシュ再配布時の表記義務を遵守する。

## 3. 配置密度・出現条件

### 3.1 配置密度（目標値・仮）

- **目標密度: 都市部・住宅密集地では概ねヘクス3〜5個（`docs/terrain.md` §3 の約50m四方ヘクス基準で150〜250m四方）に1件程度の一般オブジェクトが存在する状態を狙う。**
- 上記は Tier 1 タグのみで密度が確保できる市街地を想定した目標値であり、**Tier 1 だけで目標密度に届かない地域（郊外・山間部・農村部等）は Tier 2 タグを補完採用して密度を底上げする**（§2.1）。
- それでも極端に地物が少ない地域（人跡未踏の山岳・海上等）まで密度を無理に埋めることはしない。「大量配置で動機づけ」は主に人が生活・訪問する地域を対象とした設計であり、terrain.md §6.1 のスポーン地点保証のような**全域一律の下限保証は行わない**（本書のスコープ外、§7）。
- 具体的な密度の妥当性（多すぎて価値が薄まらないか／少なすぎて発見体験が弱くならないか）は実データ検証・balance 検討（plan/tasks 工程）で調整する。
- ボーナスオブジェクト（§2.2）は性質上、密度目標を設けない（allowlist に含まれる分だけ、全国に疎らに存在する）。

### 3.2 出現条件（現地開示 と ポイント開放 の両対応）

Issue #6 決定事項「ポイント開放マスの表示: 表示する（#4の『大量配置で動機づけ』方針と整合）。開放は離れていても可能。実際に現地へ行った場合はさらにプラスボーナスを付与し、徒歩訪問の価値を残す。」に基づき、以下の2層構造とする。

1. **未開示ヘクス上のオブジェクトの"見せ方"（動機づけの核）**
   - オブジェクトが存在するヘクスがまだ霧に覆われていても、**そのオブジェクトの存在を示すピン（アイコン。詳細名称等はロック表示）を地図上に表示する**。`docs/opening_points.md` が定義する「ポイントで開放できるマスの表示」と同じ考え方を、名所オブジェクトのピン表示にも適用する。
   - これにより「この先に何かある」「ここに行けば手に入る」という牽引力を、実際に到達する前から発生させる（大量配置方針の狙いである"発見コンテンツとしての豊富さ"を可視化する装置）。
   - ピンの詳細（名称・種別・ボーナス有無）は開放後にのみ開示する（未開示時は「？」等の伏せ表示とし、ネタバレを避けつつ期待感を作る）。
2. **収集（開放）の2手段**
   - **a. 現地開示（徒歩）**: `docs/terrain.md` の霧開放（GPS移動によるヘクス開示）でオブジェクトを含むヘクスが開示されると、そのオブジェクトを自動収集し、**現地訪問ボーナス込み**の報酬を得る（§4）。
   - **b. ポイント開放**: `docs/opening_points.md` の開放ポイント消費（§5 隣接制約・1pt/メッシュ）でヘクスを開示した場合も、同様にオブジェクトを自動収集するが、**現地訪問ボーナスは付与されない**（基本報酬のみ）。
   - いずれの手段でも「離れていても開放可能」という #4 の決定を尊重しつつ、実際に歩いた場合に上乗せ報酬を与えることで「徒歩訪問の価値」を残す（Issue #6 決定事項に明記の通り）。

## 4. ボーナスオブジェクトの効果（コレクション主体・報酬は控えめ）

Issue #6 決定事項「ボーナスオブジェクトの効果: コレクション（図鑑）＋軽い産出/ポイントボーナスの複合。収集の満足感が主、報酬は控えめにして#4の歩行優位を崩さない。」に基づき、以下のとおり定義する。

- **主効果: コレクション記録（§5 参照）**。ボーナスオブジェクトは一般オブジェクトと区別されたフラグ（`is_bonus`）を持ち、名所図鑑上で特別に扱われる（表示上のハイライト・専用セクション等の詳細UIは Issue #12 のスコープ）。
- **副効果（軽量・仮値）**:
  - 収集時、**開放ポイントの一時ボーナス +1〜3P**（`docs/opening_points.md` §4 のストック上限50を超えない範囲で加算）を付与する。現地訪問ボーナス（§3.2-2a）が乗る場合は上限側の値（+3P）、ポイント開放の場合は下限側の値（+1P）を目安とする。
  - 収集済みボーナスオブジェクトの累計件数に応じて、**街全体の産出に対する小さな倍率ボーナス**（例: ボーナスオブジェクト1件ごとに産出+0.1%、上限あり）を付与する。`docs/terrain.md` §8 の人口ボーナス（産出全体への倍率）と同系統の仕組みとして扱い、加算/上限の詳細数値は balance 検討で確定する。
  - **一般オブジェクト（Tier 1/2）は上記の産出/ポイント副次ボーナスを持たない**。図鑑記録（§5）のみ行う。豊富さで動機づける主力である一般オブジェクトに強い報酬をつけると、開放ポイント経済（歩行優位の設計、`docs/opening_points.md` §1）を崩しかねないため、報酬はボーナスオブジェクトのみに限定して控えめにする。
- 上記の数値はすべて**仮置き値**であり、balance 検討（plan/tasks 工程）で最終確定する。

## 5. コレクション/図鑑連携（Issue #12 との切り分け）

- 収集したオブジェクト（一般・ボーナス双方）は `specs/001-mvp/plan.md` §6 で定義済みの **`collection` エンティティ（名所図鑑・#6/#12統合）**に記録する。
- 本書が定義する `collection` レコードの必須項目（Issue #12 の図鑑UI/実績設計の入力となる最小データ契約）:

| フィールド | 内容 |
|-----------|------|
| `poi_id` | 地域パック `poi` テーブルの ID（§2） |
| `kind` | オブジェクト種別（OSM タグ由来。例: `tourism=attraction` 等） |
| `is_bonus` | ボーナスオブジェクトか否か（§2.2） |
| `collected_at` | 収集日時 |
| `collect_method` | 収集手段（`walk`＝現地開示 / `point`＝ポイント開放。§3.2） |
| `bonus_granted` | 収集時に付与された副次ボーナス値（§4。ボーナスオブジェクトのみ） |

- **図鑑としての見せ方（達成率表示・称号・実績解除等）、および他の実績（歩行距離・区画制覇等）との統合UIは [Issue #12「実績・称号・コレクション図鑑」](https://github.com/rokusoudo-product/terra-town/issues/12) のスコープとし、本書では扱わない**。本書は Issue #12 が消費できる最小限のデータ契約（上表）を定義するに留める。
- Issue #12 は本書執筆時点で `ready` ラベル未付与（代表実装GO待ち）のため、本書の記述はあくまで Issue #12 着手時の入力として先行定義する位置づけである。

## 6. #4「大量配置で動機づけ」方針との整合まとめ

受け入れ基準3「#4の『大量配置で動機づけ』方針と整合している」ことの確認として、対応関係を整理する。

| #4 で確定した方針 | 本書での対応 |
|-------------------|-------------|
| 固有名所の現地限定は不採用 | §3.2 でポイント開放でも収集可能と定義（現地限定を撤廃） |
| 興味を引くオブジェクトを大量配置 | §2.1 Tier1+Tier2 の2層抽出で密度を確保（§3.1 目標密度） |
| 希少なコレクションではなく豊富さで動機づけ | 一般オブジェクトは無報酬・大量配置に振り切り（§4）、ボーナスのみ希少・軽報酬 |
| ポイント開放マスの表示（#4決定・本Issueにも適用） | §3.2-1 で未開示オブジェクトのピン表示（ロック状態）を定義 |
| 徒歩訪問の価値を残す | §3.2-2a 現地訪問ボーナス、§4 副次ボーナスの上下差で担保 |

## 7. スコープ外（本Issueでは扱わない）

- allowlist（`bonus_landmarks.csv` 相当）の具体的な収録件数・収録地物の最終リスト（plan/tasks 工程でデータ整備）。
- Tier 1/Tier 2 タグセットの最終確定・地域別の抽出パラメータ調整（実データ検証を経て plan/tasks 工程）。
- 産出/ポイントボーナスの最終数値（§4 の +1〜3P・+0.1%等はすべて仮値。balance 検討で確定）。
- 名所図鑑のUI・実績・称号設計（[Issue #12](https://github.com/rokusoudo-product/terra-town/issues/12) のスコープ）。
- 人跡未踏エリア（山岳深部・海上等）に対する密度下限保証（§3.1。terrain.md §6.1 のスポーン地点保証とは別の話であり、本Issueでは導入しない）。
- 近接通知（未開放の名所をプッシュ通知で知らせる仕組み）は [Issue #14](https://github.com/rokusoudo-product/terra-town/issues/14) のスコープ。
