# terra-town — エリアの形と地形タイプ定義

> 本書は [Issue #3](https://github.com/rokusoudo-product/terra-town/issues/3)「エリアの形と種類の定義」の受け入れ基準を満たすための設計ドキュメント。
> `specs/001-mvp/spec.md` §5（マップ設計方針）§6（ゲーム内経済）を具体化する。
> 実装言語・ゲームエンジン・地図SDK（spec.md §11-8）が未確定のため、本書はコードではなく仕様定義として扱う。
> 実装フェーズでは `C:\Users\moets\.claude\GPS_ARCHITECTURE.md`（`core/` は `location/` を import しない一方向依存）に従うこと。
> 地形タイプ判定・産出計算・建築状態管理は `core/` 相当の純粋ロジックとして実装し、OSMデータ取得・座標変換は `location/` 相当のモジュールに置く。

## 1. マスの表現軸（地形軸 × 建築状態軸）

1マス（ヘクス）は **地形タイプ軸** と **建築状態軸** の直交する2軸で表現する。この2軸は独立して管理し、互いを兼ねない。

```
マス = (地形タイプ, 建築状態)
```

- **地形タイプ軸**: そのマスの土地としての性質（空き地・森・山・水辺・海）。自然資源の一次産出を決める（Issue #70・2026-09-08 代表決定により農地・市街を除外。文明〔畑・農場・工場・住宅等〕はプレイヤーが空き地に建設する対象として `docs/buildings.md` に一本化した）。
- **建築状態軸**: そのマスに建物が建っているかどうか（未建築 / 建築後）。プレイヤーの行動（建設）で変化する。

2軸を分離する理由:
- 「森のまま建物を建てる」ような矛盾を防ぎつつ、将来「地形タイプの変更」（例: 森を伐採して空き地にする）と「建築」を独立したアクションとして扱える。
- 産出ロジック（地形タイプ由来）と建築ロジック（建築状態由来）を疎結合にでき、`core/` 内でテストしやすい。

### 1.1 建築状態軸

| 状態 | 説明 |
|------|------|
| 未建築 | 建物が建っていない状態。地形タイプに応じた基礎産出のみ発生 |
| 建築後 | 建物が建っている状態。建物の種類・レベルに応じた効果が追加される（詳細は建物システムとして別途定義） |

- 建築状態を「建築後」にできるのは、地形タイプが **空き地** のマスのみ（後述 §2）。
- 建築後の地形タイプは引き続き「空き地」のまま扱う（＝建築は地形タイプを上書きしない。建物の存在は建築状態軸のみが表す）。

## 2. 地形タイプ一覧（5種・Issue #70で農地・市街を除外）

> **2026-09-08 代表決定（Issue #70）**: 地形タイプから**農地・市街を除外**し、7種から5種にした。
> 「**地図が与えるのは自然、文明はプレイヤーが建てる**」という設計思想に基づき、文明（畑・農場・工場・住宅等）は
> 地形として固定配置されるものではなく、プレイヤーが空き地に建設する対象として `docs/buildings.md` に一本化する。
> これにより、旧・地形産出（農地→野菜/フルーツ）と建物産出（畑→野菜/フルーツ）の**二重定義が解消**された
> （`specs/001-mvp/spec.md` §6 参照）。

| 地形タイプ | 産出資材 | 建築可否 | 備考 |
|-----------|---------|---------|------|
| 空き地 | なし（産出0、建築の土台） | 可 | 唯一、建物を建てられる地形。建築後は「空き地＋建築後」として扱う |
| 森 | 木 | 不可 | 伐採により空き地化する変更手段あり（§6） |
| 山 | 石・鉄 | 不可 | |
| 水辺（川・湖） | 水 | 不可 | |
| 海 | 塩 | 不可 | 建築不可だが開放対象（§7）。内陸スタートでの塩入手可否は Issue #72 のスコープ（§6.1参照） |

- 資材体系は `specs/001-mvp/spec.md` §6 の建設系（木・石・鉄）／生活系（塩・水・野菜・フルーツ・肉）と対応する。地形が産出するのは自然資源の一次産出（木・石・鉄・水・塩）のみであり、野菜・フルーツ・肉は建物産出専用（`docs/buildings.md` §6）。
- 空き地は産出を持たないが、プレイヤーが建物を建てて発展させるための地形。産出ゼロの地形が偏ると詰みうるため、スポーン周辺の配置方針（§6.1）で担保する。
- **旧・農地／市街の扱い**: 除外前に農地・市街と判定されていた OSM タグ（`landuse=farmland`/`orchard`/`vineyard`/`meadow`/`residential`/`commercial`/`industrial`/`retail`）は、いずれもフォールバックの**空き地**に統合する（§5参照）。農地相当の土地は「畑」「農場」、市街相当の土地は住宅系の建物として、プレイヤーが空き地に建設することで表現する。
- 人口メカニクス（旧・市街の人口ボーナス）は `docs/buildings.md` §5 に一本化済み（§8参照）。

## 3. ヘクスサイズ

- **1ヘクスの対辺（辺と向かい合う辺の距離）は約 50m** とする（仮置き、プロトタイプで調整）。
- 採用理由: 徒歩数十歩〜1分未満で隣接ヘクスへ移動できる粒度感を狙う。細かすぎるとGPS誤差（数m〜十数m）で地形判定がぶれ、粗すぎると「歩いた実感」が薄れるため、50m前後を初期値とする。
- 数値は `balance` 検討（plan/tasks工程）で最終調整する。変更する場合は本書を更新すること。

### 3.1 採用解像度（H3 res 11）と実測値（2026-09-08・Issue #38）

- ヘクスID体系として **H3**（Uber のグローバルヘクスグリッド索引。§4.2）を採用したため、ヘクスサイズは H3 の**固定解像度**から選ぶ必要がある（任意の値を取れない）。
- H3 は解像度ごとに平均セルサイズが定まっている。50m に最も近い解像度を**実測**して選定した（`h3` Python パッケージ 4.5.0・推測ではなく計算で比較。比較した全解像度の数値は `specs/001-mvp/research.md` §8.2 参照）。
- **採用: 解像度11**。
  - 平均対辺（`average_hexagon_edge_length` から算出。対辺 = 辺長 × √3）: **約49.65m**
  - 対象エリア（bbox中心座標）の実セルで実測した対辺（6頂点の対辺中点間の測地距離平均）: **約47.68m**
  - 50mとの差: 平均値ベースで約0.35m、実測ベースで約2.32m。
- **差を許容する理由**: 本節冒頭のとおり §3 は「仮置き、プロトタイプで調整」と明記されており、50mという数値自体が「徒歩数十歩〜1分未満」という体感重視のラフな目安であって、ゲームバランス上の厳密な確定値ではない。H3 res11（約48〜50m）はこの目安の範囲に十分収まっており、かつ解像度10（平均約131m・実測約127m）は50mから乖離が大きく、解像度12（平均約18.8m・実測約18.1m）は細かすぎて「隣接ヘクスへの移動」の体感が薄れる。res11 が両側の候補より明らかに50mへ近いため採用する。最終的な体感バランス調整は引き続き balance 検討（plan/tasks工程）で行う。

## 4. 内部判定はグリッド、UI表示のみヘクス（折衷方式）

### 4.1 折衷方式の概要

2026-07-22 代表決定により、以下の折衷方式を採用する。

- **内部の開示判定・資材判定**: 緯度経度ベースの矩形グリッド（例: 数m四方の細分セル）に対して行う。GPS座標・OSMタグとの突き合わせは緯度経度のまま扱う方が実装・精度管理ともに単純なため。
- **UI表示**: プレイヤーに見せるマス目のみ、六角形（ヘクス）として描画する。デザイン性・拡張性（隣接6方向の演出のしやすさ等）を重視。
- **変換**: 複数の細分グリッドセルを1つのヘクスに集約し、セル群の地形タグの多数決（面積比が最大のタイプ）でヘクス全体の地形タイプを1つに確定する（§5 判定ルール参照）。開示判定（霧が晴れているか）もヘクス単位で集約する。
- この方式により、`core/`（判定ロジック）は緯度経度グリッドの矩形セル列を入力に取る形で実装でき、ヘクス座標系（表示用のみ）への依存を持たない。ヘクス⇔グリッドの変換は `location/` または表示レイヤーの責務とする。

### 4.2 ヘクスID体系: H3 の採用（代表決定 2026-09-08・Issue #38）

`HexId`（Issue #33。`packages/core/lib/src/geo/hex_id.dart`）は非負整数を保持するだけの値オブジェクトとして実装されており、緯度経度→ID変換のロジック自体は意図的に `core` に置かれていない（2026-08-11 代表回答）。しかし変換方式そのものがどこにも定義されていなかったため、パック生成側（`tools/pack-builder/`）と実行側（`location/`）が同じ座標から同じ整数を出せず破綻するリスクがあった。本節でこれを確定する。

- **採用: Uber の H3**（グローバルなヘクスグリッド索引）。
- 理由:
  - 64bit整数のインデックスを標準で持ち、`HexId` が非負整数であるという既存の設計と整合する。
  - 決定論的で、**Python（`h3` パッケージ）と Dart（`h3_dart` / `h3_flutter`）の双方に実装があり**、生成側と実行側で同じ緯度経度から同じ値を再現できる。独自方式を2言語で二重実装する理由がない。
  - 全球をカバーするインデックスであり、「地球が自分の街になる」という将来像と矛盾しない。
  - §4.1 の「細分グリッドセルで地形判定 → 各セルを包含するヘクスへ割り当て → 多数決で集約」という流れをそのまま実装できる（§4.1 の「内部判定は矩形グリッド、表示のみヘクス」という設計を崩さない）。
- **バージョン**: H3 は v3 と v4 で API・挙動が異なる。本 Issue で検証・採用したのは **H3 v4 世代の API**（Python `h3` 4.5.0・関数名 `latlng_to_cell`/`cell_to_latlng` 等）であり、Dart側で使う場合は `h3_dart` のうちバンドルする H3 コアが v4 世代のバージョン（`h3_dart` 0.7.0 で確認済み。関数名 `geoToCell`/`cellToGeo` 等、v4相当のAPI体系）を使うこと。v3世代のライブラリ（関数名 `geoToH3`/`h3ToGeo` 等）と混在させないこと。詳細は `specs/001-mvp/research.md` §8.3 参照。
- **解像度**: §3.1 のとおり **解像度11** を採用する。

### 4.3 緯度経度 → 細分グリッドセル → H3ヘクス の導出手順

生成側（`tools/pack-builder/`）と実行側（`location/`）の両方が「同じ緯度経度から同じ整数（H3 index）」を導けることが本節の目的。両者が実際に一致させる必要があるのは**手順2（緯度経度→H3セル）のみ**であり、手順1（グリッド細分化）はパック生成時にのみ必要な内部処理である点に注意。

1. **パック生成時のみ（`tools/pack-builder/`）**: 対象エリアを細分グリッドセル（§4.1。現在の実装値・妥当性は `research.md` §8.1 参照）に敷き詰め、セルごとに §5 の優先順位ルールで地形タイプを1つ確定する（= `cell_terrain` 相当）。
2. **生成側・実行側で共通（必ず一致させる手順）**: 対象の緯度経度（生成側では各セルの代表点、実行側ではプレイヤーの現在地）を、**固定解像度11**で H3 セルインデックスに変換する。
   - Python（生成側）: `h3.latlng_to_cell(lat, lon, 11)` → 16進文字列 → `h3.str_to_int(...)` で64bit整数化。
   - Dart（実行側・`location/`）: `h3_dart` の `geoToCell(GeoCoord(lat: lat, lon: lon), 11)` → `H3Index`（`BigInt`）。
   - H3 は公開仕様に基づく決定論的アルゴリズムであり、同一の実装世代（§4.2 のとおり v4世代同士）であれば言語が異なっても同じ緯度経度・同じ解像度から同じインデックス値が得られる。これは H3 自体の設計目標であり、本 Issue の実測でも Python側の値をそのまま使えることを確認している（`research.md` §8.4）。
3. **パック生成時のみ**: 同じ H3 セルに属する複数の細分グリッドセルを、地形タイプの多数決（セル数最大。同数の場合は §5 の優先順位が高い方を採用する決定論的なタイブレーク）で1つの地形タイプに確定し、`hex_terrain(hex_id, terrain_type)` としてパックに格納する。

実行側は `hex_terrain` を読むだけであり、手順1・3を再実装する必要はない。実行側が必要とするのは手順2（現在地→H3セルインデックス）と、そのインデックスをキーにした `hex_terrain` の検索だけである。

### 4.4 H3 index → 地図 Feature の `id` の橋渡し（Issue #38・2026-09-08 代表決定）

fog of war は全ヘクスを1回だけ GeoJSON ソースとして地図に追加し、以後 `setFeatureState` でヘクス単位に開示をトグルする方式を採用している（plan.md §8）。Android では `promoteId`（`properties` の値を feature id に昇格する機能）が使えないため、**各 Feature は直下に整数 `id` を持つ必要がある**（2026-08-13 Issue #38 コメント）。

一方 H3 index は64bit整数（概ね10^18台）であり、**JSON の安全整数の上限（2^53-1 ≒ 9.007×10^15）を超える**。そのため H3 index をそのまま Feature の `id` に載せると、Android側でのJSONパース時に数値精度が落ちる可能性がある。

- **採用方式: 下位52bitマスク**。`feature_id = h3_index & ((1 << 52) - 1)`。
  - 52bitの最大値（4,503,599,627,370,495）は2^53-1未満であり、JSONの安全整数の範囲に収まる。
  - 同一パック（＝同一エリア＝同一解像度）内では、H3 index の上位12bit（reserved・mode・resolution）が全セルで共通の定数になるため、下位52bit（base cell 7bit + 各解像度の方向桁 最大45bit）だけで**同一パック内の一意性は失われない**（実測で衝突ゼロを確認。`research.md` §8.4）。
  - fog of war の feature-state はソース単位（＝1エリア＝1パック、plan.md §3.2）で完結するため、他パックとの間で `feature_id` が衝突しても問題ない。
- **`plan.md` §3.3 の不変性を壊さない理由**: `feature_id` は `h3_index`（＝緯度経度と解像度から一意に決まる値）だけから決まる**純関数**であり、パックの生成回数・ヘクスの列挙順・生成時刻など「その回の生成」に依存する要素を一切含まない。したがって同じ場所のヘクスは、パックを何度作り直しても常に同じ `feature_id` になり、`disclosed_hex`（開示履歴）が指すヘクスの同一性が壊れない。
  - **退けた案1（パック単位の連番採番）**: 1,2,3,... のような連番は「その回の生成でのヘクスの列挙順」に依存するため、OSMデータ更新やbbox変更で列挙順が変わると同じ場所でも別のIDになりうる。`disclosed_hex` の不変性を壊す恐れがあるため不採用。
  - **退けた案2（`properties` への格納 + `promoteId`）**: `promoteId` はWeb専用でAndroidでは機能しないため不採用（2026-08-13コメント）。
  - **退けた案3（ハッシュ化）**: SHA256等のハッシュは非可逆で、`feature_id` から `h3_index` を復元できず、逆引きが必要な場面（タップされた feature_id からヘクスの地形属性を引く等）で不便。52bitマスク方式は可逆（`h3_index = (header << 52) | feature_id`、`header` はパック内共通の定数）であるため、この点でも優位。
  - 実装は `tools/pack-builder/hex_bridge.py`（生成側の参照実装）を参照。`location/` 側で Dart 実装する際も同じマスク値（下位52bit）を用いること。
- `hex_terrain` テーブルには **`hex_id`（H3 indexの正、64bit整数）と `feature_id`（52bitマスク後、GeoJSON用）の両方**を保持する。SQLiteのINTEGERは64bit符号付きのため `hex_id` をそのまま格納できる（H3 indexは常に2^63未満であるため符号ビットも問題にならない。実測: `research.md` §8.4）。
- **`HexId.value`（`packages/core/lib/src/geo/hex_id.dart`）が保持すべき整数は、本節の `hex_id`（＝H3 indexそのもの。マスク前の64bit整数）である。** `feature_id`（地図Feature用の52bitマスク後の値）は `HexId.value` とは別物であり、`location/` が地図に渡す直前に `hex_id`から導出する（`hex_bridge.py`の`h3_to_feature_id`と同じ計算をDart側でも実装すること）。`core`は`HexId`（＝H3 index）だけを扱い、`feature_id`という概念そのものを知らなくてよい（`core`は地図SDKに依存しないという既存方針・GPS_ARCHITECTURE.mdと整合）。この区別を誤って`HexId`に`feature_id`（マスク後の値）を持たせてしまうと、`hex_terrain`（SQLite・`hex_id`列で検索）とのIDが一致せず不整合を起こすため注意。

## 5. OSMタグ → 地形タイプ判定ルール（初期版）

グリッドセル単位でOSMのタグと交差判定を行い、地形タイプを決定する。**複数タグが同一セルに重なる場合は、以下の優先順位（上が優先）で1つに確定する。** ヘクス単位への集約はセル多数決（§4）で行う。

| 優先度 | 地形タイプ | 判定タグ例（OSM） |
|--------|-----------|-------------------|
| 1（最優先） | 海 | `natural=coastline` の海側、`natural=bay`、`place=sea`、`natural=water` かつ `water=sea` |
| 2 | 水辺（川・湖） | `natural=water`（`water=lake` 等）、`waterway=river` / `waterway=stream` / `waterway=canal`、`natural=wetland` |
| 3 | 山 | `natural=peak`、`natural=mountain_range`、`natural=bare_rock`、`natural=scree`、`landuse=quarry` |
| 4 | 森 | `landuse=forest`、`natural=wood` |
| 5（フォールバック） | 空き地 | 上記いずれにも該当しないセル（`landuse=grass`、`landuse=greenfield`、`landuse=brownfield`、道路・未分類地含む。**Issue #70（2026-09-08）により農地・市街相当のタグもここに合流**、下記参照） |

- 優先順位は「産出が特徴的で希少な地形」を上位に置く考え方（海・水辺・山は局所的に貴重、森は面的に広い、空き地は残余カテゴリ）。
- **農地・市街相当のタグの扱い（Issue #70・2026-09-08 代表決定）**: `landuse=farmland` / `orchard` / `vineyard` / `meadow`（旧・農地）、`landuse=residential` / `commercial` / `industrial` / `retail`（旧・市街）は、地形タイプとしては独立させず、いずれも優先度5のフォールバック「空き地」に統合する。実データ上も、既に街に見える場所（幹線道路沿いでポリゴンタグがない区画等）が空き地判定になる例が確認されており（`specs/001-mvp/research.md` §8.8参照。旧・農地/市街判定当時の抜き取り検証は§8.5）、扱いとして一貫する。農地・市街だった土地の性質は、プレイヤーが建てる建物（畑・農場・住宅系等、`docs/buildings.md`）で表現する。
- 本ルールは初期版であり、実データでの検証（誤判定・地域差）を経て plan/tasks 工程で精緻化する。
- 道路タグ（`highway=*`）は本Issueのスコープ外（§9参照）。現時点では地形判定に使わず、下地の地形タイプ（多くは空き地）に委ねる。

### 5.1 Issue #38（`tools/pack-builder/` 最小プロトタイプ）の実データ検証で判明した事項

> **【Issue #70（2026-09-08）による補足】** 下記1点目（`landuse=retail` の市街への追加）は、市街が地形タイプとして存在していた当時の記録である。Issue #70 により市街は地形タイプから廃止され、`landuse=retail` を含む市街判定タグ（`landuse=residential`/`commercial`/`industrial`/`retail`）はすべて優先度5のフォールバック「空き地」に統合された（§5参照）。当時「市街として拾うべきか」を検討した論点自体は、現在は「フォールバックの空き地に一貫して合流させる」という結論に収束したため実質的に解消しているが、判定ルールの変遷の記録として本節はそのまま残す。

- **`landuse=retail` を市街（優先度6）に追加（2026-09-08・Issue #38時点の記録）**: 当初は `landuse=residential`/`commercial`/`industrial` のみだったが、実データ検証（狭山湖周辺、`research.md` §8）で大型小売店舗の敷地（コストコ入間倉庫店・三井アウトレットパーク入間など、実在の `landuse=retail`）が該当なしとなり空き地にフォールバックしていたことが判明した。小売店舗の敷地は実態として市街地の一部であるため追加した。
- **【要確認・未修正】`natural=peak` による山判定の妥当性**: 実データ検証で、`natural=peak`（山頂を表す「点」タグ）にバッファを掛けて山と判定したヘクスが、周囲を森林（`landuse=forest`/`natural=wood`）に囲まれた樹林帯の中の一地点であるケースが複数確認された（例: 標高131m/192mの丘陵地の山頂ノード。`research.md` §8.5 参照）。OSM上、樹林に覆われた山体そのものを「山」として面的にタグ付けする慣行がないため、`natural=peak` のような点タグに依存する限り、実際の山の大部分は本ルール上「森」に分類され続ける（山頂ノードの周辺だけが本ルールにより例外的に「山」になる）。これは §5 のルール自体の不備というより、**OSMのタグ体系が「山」という地物を面として持たない**という構造的な制約であり、対処には標高・傾斜データ（DEM等）の別途導入が必要になる可能性がある。本プロトタイプでは既存ルール（§5表・`natural=peak` を含む）を変更せずに据え置き、この論点を代表確認事項として残す（コード側の扱いは `tools/pack-builder/terrain_rules.py` のコメント参照）。

## 6. スポーン地点周辺の固定地形配置 と 地形タイプ変更手段

### 6.1 スポーン周辺の固定配置方針

- OSMの実データだけに依存すると、スポーン地点（初回起動位置）周辺が海・山などの単一地形に偏り、**産出ゼロで詰む**リスクがある。
- これを避けるため、スポーン地点から一定半径（目安: 数ヘクス〜十数ヘクス圏内、具体半径は plan/tasks で確定）については、以下を保証する。
  - スポーン地点そのもののヘクスは必ず **空き地**（＝プレイヤーが即座に建築を始められる）。
  - 半径内に、産出資材の主要カテゴリ（建設系・生活系それぞれ最低1種）を確保できる地形タイプが最低1ヘクスは存在する。
  - 実データ判定の結果、上記条件を満たさない場合は、**決定論的な補正**（スポーン地点の座標から一意に導かれるシード等を用いて、不足している地形タイプを近傍の空き地/低優先度セルに上書き配置する）で最低限の多様性を確保する。補正はプレイヤーごとに固定・再現可能とし、同じスポーン地点なら常に同じ配置になるようにする。
- 詳細な半径・補正アルゴリズムは plan/tasks 工程でバランス調整とあわせて確定する。
- **【要確認・Issue #72で扱う】生活系資材の確保について**: 地形タイプが5種になったことで、**海が唯一の塩の供給源**になった。内陸スタートでは半径内に海ヘクスが存在せず、上記「生活系最低1種」の保証が塩に関して成立しない可能性がある。石・鉄（山への依存）と同型の「特定地形に依存し、その地形が手に入らない立地がある」という構造の問題であり、解決策も同じ枠組み（建物・加工による代替供給経路の新設等）で設計できるため、**本Issue（#70）では扱わず [Issue #72](https://github.com/rokusoudo-product/terra-town/issues/72) のスコープとする**（2026-09-08 代表決定）。

### 6.2 地形タイプ変更手段（概要）

- 森・山・水辺などの非空き地は、初期状態では建築不可だが、**プレイヤーの行動によって地形タイプを空き地に変更できる**手段を用意する（例: 森を伐採して空き地化する）。
- 概要のみ本書で定義し、具体的な変更手段・必要資材・コストは plan/tasks 工程で設計する。
  - 想定: 対象地形に応じた行動（伐採＝森 等）と、行動に必要な資材コスト・実行条件（対象マスが開示済みであること等）を設ける。
  - 海は変更対象外（建築不可のまま）とする。

## 7. 海の開放・産出・ボーナスタイル方針

- **建築**: 不可（陸上の空き地のみが建築対象、§2）。
- **開放（霧を晴らす対象に含む）**: 海ヘクスも他の地形と同様に「開放対象」に含める。徒歩到達（実際に海沿いを歩いて隣接する等）でもポイント消費による開放でも、いずれの手段でも開放できる。
- **産出**: 開放済みの海ヘクスからは **塩** を産出する。
- **ボーナスタイル**: 海上には通常の海ヘクスとは別に「開放ボーナスタイル」（特殊オブジェクト）を一定間隔・条件で配置する。開放すると通常の塩産出に加えて特別な報酬（詳細は balance/tasks 工程で設計）を得られる。名所・観光POIオブジェクト（spec.md §3.1 V-B）の海版という位置づけ。
- 陸地に閉じない開放範囲にすることで、海岸沿いのユーザー体験を担保する（spec.md §11-2 開始位置ぼかしとも整合させ、海の開放自体はプライバシー方針の対象外＝個人の自宅特定に直結しないため制約なし）。
