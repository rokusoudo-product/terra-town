# terra-town — MVP 実装計画（plan.md / ゲート②）

> 本書は spec-kit フローの `plan.md`（技術スタック・アーキテクチャ）に相当する。`spec.md`（何を・なぜ）を前提に、**どう作るか**を確定する。数値の正本は将来 `specs/001-mvp/balance.csv`。UIデザインは `DESIGN.md`、環境構成図は `docs/architecture.md`。

## 0. このゲート②で確定する要点（サマリ）

1. **フレームワーク = Flutter**（Android 先行・iOS も見据える）
2. **地図SDK = MapLibre GL Native**（map load 従量課金なし・ベクタ制御・fog of war 描画）
3. **機微処理 = ネイティブ(Kotlin)を platform channel 越しに**（背景位置・モック検出・Play Integrity・歩数）。channel 契約は **Pigeon** で型定義し iOS 移植の正とする
4. **アーキ = GPS_ARCHITECTURE 準拠**：`core/` は `location/` を import しない。core を**別 Dart パッケージに物理分離**
5. **🔴 タイル＝地域パック方式**（同梱 MBTiles ＋ 静的ホスティングから初回DL）。「BEなし」を**「自社ステートフルサーバを持たない」**と再定義
6. **🔴 資材分類＝CIで事前計算**した属性を SQLite で地域パックに同梱（実行時タイルクエリはしない＝決定論を担保）
7. **エリア単位 = ヘクス約50m（表示）＋緯度経度の矩形細分グリッド（内部判定）**（既承認 [`docs/terrain.md`](../../docs/terrain.md)＝Issue #3 の折衷方式に準拠）
8. **MVP は端末内完結**（位置・区画・建設・偽装対策すべてローカル）。ソーシャル/ランキング #16 で初めて BE 導入

## 1. 技術スタック（決定 A〜D）

| # | 決定 | 採用 | 主な理由 | 却下 |
|---|------|------|---------|------|
| A | フレームワーク | **Flutter (Dart)** | iOS も見据える単一コード／地図中心2D／宣言的UIで育成画面 | Kotlin ネイティブ（iOS二重開発）・Unity/Godot（地図統合で不利・過剰） |
| B | 地図SDK | **MapLibre GL Native** | map load 従量課金なし／自前・OSSタイルでコスト/ロックイン制御／ベクタ制御で fog of war | Google Maps（従量課金・自由度低）・Mapbox（課金/ロックイン）・osmdroid（属性連動弱） |
| C | 機微処理 | **Kotlin ネイティブ + platform channel(Pigeon)** | 背景位置・fused location・モック検出・Play Integrity・歩数センサーは OS別実装が本質。抽象化コストは Flutter でも消えない | 全て Flutter プラグイン（背景位置・整合性が弱い） |
| D | モジュール分離 | **core を別 Dart パッケージ化**（`packages/core`）＋ location/app が依存 | 依存方向をビルドで物理強制。core は GPS/地図非依存で単体テスト可能 | 規約のみの分離（破られる） |

**iOS 展開時の負担について（advisor 評価）**: モック検出・整合性API・Health・位置は元々 OS別実装が本質のため、Flutter でも二重化は避けられない。二重化を許容する代わりに **Pigeon の channel 契約ファイルを iOS 移植の正**とし、Dart 側ロジックは共通化する。→ 許容範囲。

**Flutter 地図プラグインは最大の実装リスク**（`maplibre_gl` 系 vs 新 `maplibre` パッケージ）。動的 addSource/addLayer・feature-state・ローカルタイル読込の API 露出がバージョンで不安定。→ **Issue #24（スパイク）の第一目的をプラグイン選定＋必要API疎通確認**とし、結論を本 plan に追記する（§10）。

├── tools/pack-builder/       # 地域パック生成パイプライン（Planetiler/osmium）※ビルド時のみ・実行時サーバではない

> ✅ **実態反映（2026-09-08・Issue #35）**: 当初案は `android/` `ios/` をリポジトリ**ルート**に置く構成だったが、`flutter create` の標準に合わせて実際は **`app/android/`**（`app/ios/` は将来・未着手）とした。経緯・判断根拠は `docs/dev-setup.md` §6。

## 3. 🔴 地域パック方式（タイル・地形属性・区画・POI の束）

> advisor 必須修正①。公開 OSM タイルサーバ（tile.openstreetmap.org）直叩きは **OSMF tile usage policy 違反**。かつラスタのみでベクタ feature に触れないため B 案の前提を満たせない。→ 使用しない。

### 3.1 「BEなし」の再定義
- **BEなし＝自社運用のステートフルなバックエンド（ユーザーデータを置くサーバ）を持たない**。
- **静的ファイル配信は BE ではない**。地域パックの初回DLは「地域の選択」しか漏らさず、**歩行位置はサーバに漏れない**＝プライバシー最優先の看板と両立。

### 3.2 地域パックの内容物（1エリア = 1パック）
| 内容 | 形式 | 生成元 |
|------|------|--------|
| ベクタタイル（表示専用） | **MBTiles**（第一候補）/ PMTiles（第二段） | Planetiler（OSM日本抽出） |
| セル/ヘクス地形属性（資材判定の正） | SQLite `cell_terrain` → 集約 `hex_terrain(hex_id, terrain_type)` | osmium/Planetiler で事前計算（§4・terrain.md §5 判定ルール・§4 ヘクス多数決集約） |
| 行政区域ポリゴン（当該地域・簡略化） | SQLite（トポロジ保持簡略化） | 国土数値情報 N03 |
| 名所 POI | SQLite `poi(id, lat, lon, kind, name)` | OSM 観光POI 抽出 |
| パックメタ | `pack_version` 等 | — |

### 3.3 配信・バージョニング
- **MVP（バーティカルスライス）**: 対象1エリアのパックを **アプリ同梱**（通信ゼロ・規約リスクゼロ・プライバシー完全）。
- **拡張**: 都道府県/市域単位パックを **静的ホスティング（GitHub Releases / Cloudflare R2 等）から初回DL**。オフラインファーストと整合。
- **生成は CI（Planetiler）** ＝ 配信サーバではなくビルドパイプライン。BEなし原則と両立。
- **バージョニング規約**（データモデルに明記）: OSM データは変わる。**一度開示したヘクスの資材分類は、パック更新後も過去分は不変**（獲得履歴は当時の `pack_version` で確定）。これを守らないとパック更新のたびにゲーム状態が壊れる。
- **タイル読込の要検証（Issue #24）**: MapLibre Native + Flutter プラグインでの **ローカル MBTiles 読込**（`mbtiles://`）。MBTiles を第一候補、PMTiles のネイティブ対応はプラグイン経由で不確実なため第二段。
- **2026-09-09 追記（Issue #24 実機検証・research.md §6.2）**: MBTiles が実機（Pixel 7a）で成立した（`mbtiles://` 方式で `addSource`/`addLayer` 成功・描画も目視確認済み）ため、PMTiles（第二段）は不要と判定した。ただし本節の記述は削除しない。実際の地域パック（Planetiler 生成・Issue #38 の出力）での読込はまだ確認できていないため（§8「未計測」参照）、フォールバックの選択肢として残す。

### 3.4 不採用の記録
- MapTiler 無料枠: 本番不可（クォータが全ユーザー共有・APKからキー抽出）。開発時のスタイル確認のみ。
- 国土地理院ベクトルタイル: 国内は選択肢だが OSM landuse スキーマ前提の設計と二重化するため MVP 不採用（出典明記すれば利用可、将来の代替として記録）。

### 3.5 🔴 1ソース（＝1エリア）あたりのヘクス数上限（暫定・代表決定 2026-09-07・Issue #49）

> fog of war は §8 のとおり feature-state 方式（全ヘクスを1回だけソースに追加）を採用している。ソースに載せるヘクス数には上限があり、**地域パック（1エリア=1パック、本節3.2）のエリア分割設計に直結する制約**である。

- **主基準: 起動時・エリア切替時のソース構築を 2秒以内に収めること**（ヘクス数そのものではなく時間を基準にする）。
- **暫定上限: 30,000 ヘクス／1ソース**。
- **根拠**: research.md §6.4 の実測（Pixel 7a・Java ヒープ上限256MB）。100,000ヘクスで `addGeoJsonSource`（Android 側で Gson が `FeatureCollection` に展開するメインスレッド処理）が **6,535ms**（全体の74%・合計8,885ms）かかり `OutOfMemoryError` で非決定的にクラッシュした。これを線形とみなして外挿すると **30,000ヘクスでおよそ2秒**となるため、これを暫定上限とする。なお 50,000ヘクスで「PASS」の実測記録があるが、これは開示トグル（`setFeatureState`）のみの計測でありソース構築コストを含まない（研究ノート research.md §6.4 参照）ため、この上限の根拠には使用していない。
- **暫定値である旨の明記**: 上記は Pixel 7a 1台のみの実測からの外挿であり、確定値ではない。**確定は `tools/pack-builder/`（Issue #38）着手時に 30,000 ヘクス規模で実機計測して行う**。実測が主基準（2秒以内）から乖離した場合は、その時点で本節を更新する。
- **低スペック端末対応**: 現時点ではヘクス数をさらに引き下げる対応は行わない。主基準を時間（2秒以内）に据えているため、端末が遅い場合は基準を満たすヘクス数が自動的に小さくなる設計であり、端末差は主基準の中で吸収される。#38 の実機計測で他端末の結果が得られた段階で再検討する。
- **上限超過時の方針**: 1エリアのヘクス数が暫定上限（30,000）を超える場合は、**エリアを分割して複数ソースに分ける**（エリア分割）か、**ビューポート単位で必要な範囲のみを分割ロードする**方式に切り替える。分割方式の詳細設計は `tools/pack-builder/`（#38）で決定する。

## 4. 🔴 資材分類の決定論（事前計算）

> advisor 必須修正②。実行時にベクタタイル feature をクエリして資材を決めると、**タイルのズーム簡略化・間引きで同じ場所でも判定が揺れる**（再現性なし・テスト不能・core が地図SDKに依存＝D違反）。

- **セル/ヘクス地形属性を CI でオフライン事前計算**（osmium/Planetiler で OSM 抽出 → `docs/terrain.md` §5 の OSMタグ→地形タイプ判定ルール〔優先順位付き〕を細分グリッドセルに適用 → §4 の多数決でヘクスに集約）し、SQLite で地域パックに同梱（§3.2）。terrain.md §5 が「判定ルールの正」、本 plan は「実行時でなくビルド時に事前計算する」という**実行タイミングの決定**を担う。
- 効果: (a) 判定が**決定論的**（ズーム簡略化に左右されない）、(b) `core/` は SQLite を読む純粋関数で完結、(c) タイルは**表示専用に降格**し地図SDK差し替えも容易。
- 資材マッピング（terrain.md §2・spec §6・buildings.md §6 と整合）: 森→木、山→石/鉄、水辺→水、海→塩、空き地→建築の土台（地形産出なし）。**農地・市街は Issue #70（2026-09-08）で地形タイプから除外**し、農地相当の産出（野菜/フルーツ）・市街相当の人口ボーナスは、いずれもプレイヤーが空き地に建てる建物（畑・住宅系等）側に一本化した（`docs/buildings.md` §5・§6）。肉は農場（建物）でのみ産出（#5）。
- **乱数を使う要素はシード固定**（リプレイ可能性・テスト容易性）。

## 5. エリア単位・座標系（既承認 docs/terrain.md #3 に準拠）

> **正は [`docs/terrain.md`](../../docs/terrain.md)（Issue #3・2026-07-22 承認）**。本 plan はそれに従い、実装上の抽象を定義するに留める（advisor が当初推奨した「日本の地域メッシュ125m」は #3 のヘクス折衷方式と競合するため**不採用**）。

- **表示/ゲーム単位 = ヘクス 約50m**（terrain.md §3、対辺約50m・初期値、balance で調整）。UI はヘクスで描画。
- **内部判定 = 緯度経度ベースの矩形細分グリッド（数m四方）**（terrain.md §4）。開示判定・地形判定はグリッドセルで行い、複数セルを1ヘクスに多数決集約。
- **`core/` の抽象**: `core/` はヘクス座標系（表示用）に依存しない。`core/` は事前計算済みの `HexId`／`TileId`（決定論的な緯度経度→ID変換の結果）と地形属性のみを受け取る。ヘクス⇔グリッド変換は `location/`／表示レイヤーの責務（terrain.md §4 と一致）。
- **行政区画（#7 制覇率）**: 区画は国土数値情報 N03 のポリゴンを**別レイヤーで重畳**し、ヘクス重心が区画内かで帰属判定。制覇率の分母は「区画内の到達可能ヘクス」（#7 代表回答＝到達可能のみ分母）。
- スポーン周辺の固定地形配置・地形変更手段は terrain.md §6 に従う。

## 6. データモデル・セーブ

- **ストレージ: SQLite（Drift 等）**。ゲーム状態・地域パック（読み取り専用）を分離。
- **開示ヘクス集合: Roaring Bitmap / ビットセット**で地域ごとに圧縮（GeoJSON 保持は肥大化）。
- 主なエンティティ: `disclosed_hex`（開示済みヘクス・pack_version）、`inventory`（資材）、`building`（建物・建築状態軸 terrain.md §1・区画・座標）、`district_progress`（制覇率・発展度）、`collection`（名所図鑑・#6/#12統合）、`quest_daily`（#11・端末内生成）、`settings`（プライバシーゾーン等）。
- **🔴 機種変更対策（MVP要件に昇格）**: 端末内完結の最大の弱点は「機種変更・故障＝全ロスト」。**明示的なエクスポート/インポート機能を MVP 要件に入れる**（Android Auto Backup は 25MB 上限で不十分）。エクスポートは端末内ファイル/共有シート経由（サーバに送らない）。
- オフライン同期（FR-7）: MVP は端末内完結のため「同期」は端末内のオフライン蓄積→前景復帰時の状態反映のみ（サーバ同期は #16）。

## 7. 位置記録パイプライン・電池（#10 実装方針）

- **記録は Kotlin foreground service**（fused location provider）。サンプリングは **距離ベース（移動検知）**、停止中は省電力（#10 代表回答）。距離しきい値の初期値は Issue #10 の実機計測で確定。
- **時刻は単調時計 `elapsedRealtime`** を使用（端末時刻改竄に耐性）。
- 常時高精度GPSを使わない（NFR-1）。画面OFF時の挙動・優先度を実装仕様に明記。
- Dart は記録済みデータを読むのみ。

## 8. Fog of war 実装

> **2026-08-13 更新（Issue #24 の実機計測を受けた方式変更）**: 当初の第一案（GeoJSON 差分更新）を**採用方式から外し、旧フォールバックの feature-state 方式を採用方式に格上げ**した。
> 根拠は `specs/001-mvp/research.md` §6.4（Pixel 7a 実測）。**本節の変更は代表の承認を要する。**

- **採用方式: 全ヘクスを一度だけソースに追加し、開示は `feature-state` のトグルで表現する**。
  - 起動時（またはエリア切替時）に対象ヘクスを **1回だけ** `addGeoJsonSource` で追加し、fill レイヤの `fill-opacity` を `['case', ['boolean', ['feature-state', 'revealed'], false], 0.0, 0.62]` のような **feature-state 式**で切り替える（0.62 は DESIGN.md の fog トークンの α。ここでは実装例として値を直書きしているが、実装では `location` がこの値を直書きしないこと。`app`（composition root）が DESIGN.md の `fog` トークンから導出し、`FogOfWarLayer` のコンストラクタ引数として注入する — Issue #57・注入方式）。
  - 1ヘクスの開示は `setFeatureState(sourceId, featureId, {'revealed': true})` の1回だけ。**更新コストが開示済みヘクス数に依存しない（O(1)）**。
  - **各 Feature は直下に整数 `id` を持つ必要がある**。`promoteId` は Web 専用で Android では機能しないため、`properties` からの昇格は使えない。→ **地域パック生成（`tools/pack-builder/` ・ Issue #38）はこの id を埋め込む前提で設計すること**。
  - **`maplibre_gl` 0.27.0 以降が必要**（0.26.2 の Android は `setFeatureState` が `UnimplementedError`）。**0.27.0 は 2026-08-19 に pub.dev へ公開済み**（`latest=0.27.0`）。git 依存（`ref: release-0.27.0` 固定）は採らず、`packages/location/pubspec.yaml` で pub.dev 版 `maplibre_gl: ^0.27.0` を採用する（代表決定 2026-09-07・Issue #55）。
- **不採用: 「穴あきポリゴン1枚」の GeoJSON 差分更新**（旧第一案）。実測で合格基準を大きく下回った（research.md §6.4）。
  - 更新のたびに GeoJSON 全体を再エンコードするため、1回の更新が O(n)・全体で O(n²) になる。
  - `maplibre_gl` 0.27.0 の `compute` オフロード（上流 #366 対応）は UI の応答性を改善するが**総コストはむしろ増える**（上流実装コメント: "This buys a responsive UI, not speed"）。バージョンでは解決しない。
  - ⚠️ **但し書き**: 計測した実装は、旧第一案が想定していた最適化（開示済みヘクスの boolean union によるマージ・union の isolate 実行・ビューポート近傍への限定）を**含んでいない**。最適化を入れれば基準を満たせた可能性は否定できない。それでも本方式を不採用とするのは、feature-state 方式が**最適化なしで基準を2桁上回り、かつ実装が単純**であるため。詳細は research.md §6.4 の⚠️。
- **フォールバック（第二段）**: feature-state 方式が実データで破綻した場合は、規則格子をタイル座標から手続き生成するローカルタイルプロバイダ方式に切り替える。
- **Issue #24 性能合格基準（数値）**:
  - 開示1ヘクス追加時の更新: **200ms 以内** → **✅ 達成**（feature-state 方式で max 37.7ms / median 0.3ms。**2026-09-09 に 10,000ヘクスで4回再計測し再現を確認済み**（median 0.2〜0.3ms・max 19.0〜87.9ms、いずれも基準内。research.md §6.4「2026-09-09 追加計測」））
  - ヘクス1万個開示状態でのパン/ズーム: **55fps 以上** → **△ 部分達成**（更新ループ中 56.6fps を確認。**手動パン/ズーム時の計測は2026-09-09に実施したが、計測方法の欠陥（無操作区間を fps の分母に含めていた）により判定不能だった。「未達」ではない。ハーネス側の判定指標を修正（`activeFps` 追加・別PR #78）済みで、再計測が必要**（research.md §6.4））
  - スタイル再読み込み時のちらつきなし → **✅ 達成**（2026-09-09・代表の実機目視所見:「画面の切り替えタイミングは分かるが、霧が消えて出直すように見えたり、画面が点滅するような感じはしなかった」。research.md §6.4）
- **ソース構築の一回コストは計測済み**（2026-08-14・research.md §6.4）: 100,000ヘクスで `addGeoJsonSource` 6,535.2ms（合計8,885.5ms）、`OutOfMemoryError` で非決定的にクラッシュ。この実測を根拠に**1ソース（＝1エリア）あたりのヘクス数上限**を §3 に明記した（代表決定 2026-09-07・Issue #49）。**実運用域である10,000ヘクスでも計測済み**（2026-09-09・3回計測）: `addGeoJsonSource` 約830ms（816.9〜866.7ms）・合計約1.5秒（1,497.6〜1,521.3ms）。**10,000ヘクスでは「ソース構築2秒以内」の基準を満たす**（research.md §6.4「2026-09-09 追加計測」）。この約830ms／合計約1.5秒はいずれも**初回のソース構築**のコストであり、後述の「スタイル再読み込み時のフォグ再構築」（再構築は合計2,915.0ms）とは別の操作なので混同しないこと。
- **開示状態は永続ストレージが正である（§6 の前提を実測で裏づけた・2026-09-09）**: これは §6（`disclosed_hex`・Roaring Bitmap / ビットセット）の前提を追認するものであり、plan.md が誤っていたわけではない。新たに判明したのは1点のみ: `setStyle`（スタイル再読み込み）を呼ぶと**地図側の feature-state が全て失われる**ことが実測で確認された（2026-09-09・research.md §6.4）。したがって、**地図の feature-state は描画のための派生状態であり、開示状態の正ではない**。復元は**アプリ再起動時だけでなく、任意の `setStyle` の後にも必要**である（`tasks.md` T060 に反映済み）。
- **スタイル再読み込み時のフォグ再構築コストと、それに対する MVP 方針（2026-09-09 代表決定）**: 実測（research.md §6.4）では `setStyle` → `onStyleLoadedCallback` 発火まで141.0ms、**フォグ再構築完了までは合計2,915.0ms、その間の maxFrame 559.2ms**（この2.9秒は「再構築」のコストであり、上記の「ソース構築の一回コスト」（初回構築・約830ms／合計約1.5秒）とは別の操作である。ログにある `fps 20.6` は無操作区間を分母に含む欠陥指標のため、根拠には用いない〔naive fps・参考値〕）。ちらつきは無いが、体感としては一時停止に近い。→ **MVP では実行時に `setStyle` を伴う機能を入れない**。`DESIGN.md` のアートディレクションに昼夜切替の指定はなく、天候・季節・時間帯連動（V-D）は `future` の Issue #15 であるため、この方針で失うものはない。**このコストは Issue #15 が引き受ける**。
- **未計測（実装前に確認したい事項）**:

## 9. GPS偽装対策（#9 実装方針・脅威モデル）

- **脅威モデル**: MVP は端末内完結＝**チートの被害者は本人のみ**。対策強度はこの前提に合わせる。対人被害は #16（ランキング公開）で初めて発生し、そこで Play Integrity/サーバ照合が必要になる（段階論）。
- MVP 実装: ①モック位置検出（`isFromMockProvider` 等）②速度/テレポート検出 ③歩数センサー突合。
- **速度判定は移動平均/カルマン平滑後の速度で行う**（都市部マルチパスで瞬間100km/h相当のスパイクは日常＝正規ユーザー誤検出を防ぐ）。**時速10km超はその区間だけ報酬なし・罰しない**（#9 代表回答）を実装仕様として明文化。電車内は「報酬なしで正常動作」。
- ④ Play Integrity/App Attest・⑤サーバ異常検知は **#16 まで先送り**（検証にサーバ必須のため BEなしでは無意味＝正しい段階）。

## 10. プライバシー・権限・ストアポリシー

- **開始位置ぼかし（#8）**: プライバシーゾーン半径 **500m**、MVP は自分専用（公開レイヤー分離の思想のみ担保）。端末ローカル保存で位置は端末外に出ない。

- **Health Connect（#13）**: 読み取りは **Google Play のヘルスデータ申告・承認が必要**。オプトイン。歩数プロバイダは抽象化し将来 iOS=HealthKit。
- **データセーフティ**: 「通信が発生する箇所一覧」を用意（MVP は地域パックDLのみのはず）。
- テスト戦略と絡む: `PositionProvider` のフェイク実装＋**録画済み歩行ルートのリプレイテスト**（D の分離が活きる場所）。

**R1 追記（2026-09-08、Issue #55 / PR #66 / 追跡 #67）**: R1 は「ローカルMBTiles読込・動的レイヤ操作・feature-state という必要APIが露出しているか」を検証対象として想定していたが、`maplibre_gl` 0.27.0 を実際に組み込んで最初に詰まったのはその手前の**ビルド統合**だった。しかもビルド統合には独立した2つの詰まりどころ（Blocker）があることが判明した。

- **Blocker A（解消済み・2026-09-10、Issue #67）**: AGP 9.0.1 ＋ `android.builtInKotlin=false` の組み合わせで `flutter build apk --debug` が `Could not find method kotlin()` で失敗する問題。暫定対応として `android.builtInKotlin=true` に変更していたが（PR #66）、この設定は `kotlin-android` を適用する他の Flutter プラグイン（`path_provider` 等）を一切使えなくする相互排他を生む**ブロッカー**だったことが Issue #83（PR #90）の CI 失敗により判明した（実測 2026-09-10）。上流 `maplibre/flutter-maplibre-gl` の修正 PR #1020「fix(android): apply KGP when AGP does not compile Kotlin itself」が 2026-09-08 に main へマージ済み（pub.dev は 0.27.0 のまま未リリース）であることを確認し、`packages/location/pubspec.yaml` の `maplibre_gl` をこの commit（`2dff788c650f0d49677397aae55423774aecb8f2`）への git 依存に切り替えたうえで `android.builtInKotlin` を Flutter 既定の `false` に戻した。クリーンビルドで `flutter build apk --debug` の成功と、Flutter が出していた KGP 非推奨警告が消えたことの両方を実測確認済み（詳細: research.md §6.1）。**この対応は Issue #55（2026-09-07 代表決定・pub.dev 版 `maplibre_gl: ^0.27.0` の採用）の一時的な差し戻しである**。上流が 0.27.1 以降を pub.dev にリリースし次第、pub.dev 版に戻し Issue #55 の決定に復帰する（追跡 Issue は別途起票）。
- **Blocker B（解決済み・2026-09-08 代表決定）**: `maplibre_gl-0.27.0/android/build.gradle` が Java/Kotlin のコンパイルターゲットを AGP バージョンに関係なく無条件で `JavaVersion.VERSION_21` / `JVM_21` に固定しているため、JDK 21 でのビルドが別途必須だった。**JDK をプロジェクト既定として 17 → 21 へ引き上げることを決定した**（`ci.yml` の `java-version`・`docs/dev-setup.md` §2 を同一PR＝#66 で更新済み、`tools/check_toolchain_versions.sh` PASS 確認済み）。

  **この決定は §8 の fog of war 方式決定から強制されるものである**: §8 で承認済みの feature-state 方式は Android で `setFeatureState` が動く `maplibre_gl` 0.27.0 以降を前提としており（0.26.2 は `UnimplementedError`）、その 0.27.0 が JDK 21 を無条件で要求する。JDK 21 を採らない場合は §8 の fog of war 方式の決定そのものを開き直す必要があり、割に合わないと判断した。JDK 21 は LTS で AGP 9.0.1 / Kotlin 2.3.20 いずれとも対応する。Issue #67（Blocker A `builtInKotlin=true` の撤去条件）とは独立した制約で、上流の Built-in Kotlin 対応が進んでも本件（JDK 21 要求）は解消しない。詳細は research.md §6.1。

**R1 追記（2026-09-09、Issue #24 実機検証）**:

| 検証項目 | 結果 | 実施日 |
|---|---|---|
| ローカル MBTiles 読込（`mbtiles://`） | ✅ | 2026-09-09 |
| 動的 `addSource` / `addLayer` | ✅ | 2026-08-13 |

`feature_id` の往復は、当初の R1 検証項目には無かった追加確認である（2^53 を超える値が double 経由で静かに丸められるリスクの検証。research.md §6.3）。

**結論: R1 合格。ゲート②（技術スタック）の差し戻しは不要。**
